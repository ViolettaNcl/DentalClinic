# Развёртывание и сопровождение

[Документация](README.ru.md) · [README проекта](../README.ru.md) · [English](en/DEPLOYMENT.md)

Репозиторий настроен для контейнерного сервиса ASP.NET Core 10 в Vercel с внешней SQL Server. `Dockerfile.vercel` собирает приложение, `vercel.json` направляет трафик в сервис `app`.

Целевой адрес: [dental-clinic-vn.vercel.app](https://dental-clinic-vn.vercel.app/). Наличие адреса в конфигурации не подтверждает доступность сайта или соответствие опубликованной версии текущему коду.

## Политика выпуска

В `vercel.json` установлено `git.deploymentEnabled: false`; это закреплено тестом `tests/js/vercel-deploy-policy.test.js`. Автоматическое развёртывание Vercel по событиям Git приостановлено.

**Это не отключает GitHub Actions.** Push в `main`, в том числе только с документацией, запускает CI и может привести к публикации образа в GHCR, выгрузке по FTPS при настроенных секретах и обслуживанию реестра контейнеров.

Выпуск в Vercel выполняет уполномоченный сопровождающий через панель или настроенный CLI. Возврат автоматических выпусков требует отдельного согласованного изменения конфигурации, теста и проверки окружений.

## Конфигурация

Секреты задаются в настройках окружения, не в Dockerfile, исходниках или документации.

| Переменная | Назначение |
|---|---|
| `ConnectionStrings__DefaultConnection` | Обязательное подключение к SQL Server/Azure SQL |
| `Jwt__Key` | Обязательный случайный ключ HMAC, не менее 32 UTF-8 байт |
| `Jwt__Issuer`, `Jwt__Audience` | Обязательные параметры проверки токенов |
| `Jwt__ExpiryMinutes` | 5–1440 минут; по умолчанию 120 |
| `CRON_SECRET` | Обязательная защита служебных маршрутов на Vercel |
| `AllowedOrigins__0` | Доверенный адрес браузерного приложения |
| `Clinic__Phone`, `Clinic__Email`, `Clinic__Address`, `Clinic__Hours` | Публичные контактные данные клиники |
| `Clinic__Latitude`, `Clinic__Longitude` | Необязательная полная пара координат |
| `Scheduling__TimeZoneId` | Часовой пояс; по умолчанию `Europe/Moscow` |
| `Scheduling__AppointmentDurationMinutes` | Длительность приёма; по умолчанию 60 |
| `Scheduling__SlotIntervalMinutes` | Шаг расписания; по умолчанию 30 |
| `Scheduling__MinimumLeadMinutes` | Минимальное время до приёма; по умолчанию 30 |
| `Gemini__ApiKey` | Генерация ответов и перевод |
| `ElevenLabs__ApiKey`, `ElevenLabs__VoiceId` | Необязательное озвучивание |
| `Chat__MessageRetentionDays` | Хранение сообщений: 1–365 дней, по умолчанию 30 |
| `Chat__IpRetentionHours` | Хранение IP-псевдонимов: 1–168 часов, по умолчанию 24 |
| `ChatKnowledge__MaxItems` | Количество элементов контекста; по умолчанию 12 |
| `BackgroundJobs__CleanupEnabled` | Отмена устаревших заявок; по умолчанию выключена |
| `AdminExports__MaxRows` | Лимит строк экспорта; по умолчанию 25 000 |
| `Database__*` | Ограничения команд, подключения и пула |

При раскрытии секрета немедленно отзовите и замените его. Удаления текста из истории недостаточно.

## База данных

Контейнер Vercel не содержит SQL Server. При запуске приложение применяет миграции через `Database.MigrateAsync()`, затем выполняет `DbSeeder`. Начальное заполнение защищено SQL application lock от параллельных запусков.

Перед выпуском с миграцией:

1. Подготовьте резервную копию и проверьте возможность восстановления.
2. Просмотрите `Up`, ограничения данных и совместимость старой/новой схемы.
3. При необходимости согласуйте окно обслуживания.
4. Контролируйте применение миграций по журналам запуска.
5. Проверьте `/health`, `__EFMigrationsHistory` и основные сценарии на тестовых данных.

Возврат старой версии приложения **не откатывает БД**. Не используйте разрушающий `Down` без проверки совместимости и плана восстановления.

Seeder не создаёт администратора. Первый супер-администратор подготавливается владельцем развёртывания отдельно, с уникальным сильным паролем.

## Выпуск в Vercel

В панели проверьте проект, репозиторий, корень `.`, выбранную ветку/коммит, секреты и резервную копию. Запустите согласованный выпуск, дождитесь готовности, изучите журналы и выполните проверки ниже.

В уже авторизованной и привязанной к нужному проекту среде:

```bash
npx vercel deploy
npx vercel deploy --prod
```

Сначала проверяется Preview, затем выпускается тот же проверенный код в Production. Токены CLI не должны попадать в документацию и переписку.

Vercel завершает TLS и задаёт `PORT`; контейнер слушает `${PORT:-8080}`. Обработка перенаправленных заголовков включается только при `VERCEL=1`, с ограничением в один переход. Списки доверенных прокси/сетей очищаются в коде: инфраструктура обязана исключать прямые запросы с поддельными заголовками.

## Служебные задачи

На Vercel фоновые обработчики отключены, поскольку контейнер может приостанавливаться. Расписание в `vercel.json` задано в UTC:

| Время ежедневно | Маршрут | Назначение |
|---|---|---|
| 06:00 | `/api/maintenance/reminders` | Напоминания о приёмах следующего дня по времени клиники |
| 06:10 | `/api/maintenance/follow-ups` | Уведомления после посещения |
| 06:15 | `/api/maintenance/cleanup` | Отмена устаревших заявок, только если явно включена |
| 06:30 | `/api/maintenance/chat-retention` | Очистка IP-псевдонимов и сообщений |

Запросы требуют `Authorization: Bearer <CRON_SECRET>`. При отсутствии секрета доступ закрыт. Флаги и ключи идемпотентности защищают уведомления от повторного создания.

В длительно работающей среде предусмотрены фоновые обработчики заявок. Для хранения чата отдельного фонового обработчика нет: вне Vercel вызов `chat-retention` нужно планировать самостоятельно.

## GitHub Actions

| Файл | Назначение |
|---|---|
| `ci.yml` | Сборка приложения/контейнера, обнаружение миграций, .NET- и JS-тесты |
| `codeql.yml` | Анализ C# и JavaScript/TypeScript |
| `cd.yml` | Тесты перед публикацией, условная доставка по FTPS, образы GHCR |
| `e2e.yml` | Playwright для опубликованного приложения |
| `production-smoke.yml` | Проверки здоровья, адресов, заголовков, API и HTTPS |
| `denta-live-smoke.yml` | Проверка Gemini при наличии настроенного секрета |
| `vercel-vcr-retention.yml` | Управление сроком хранения образов Vercel |

FTPS требует четырёх настроенных FTP-секретов; иначе этот шаг пропускается. GHCR публикует `latest` и тег коммита после тестов. Эти действия не подтверждают выпуск в Vercel.

## Docker Compose

```powershell
Copy-Item .env.example .env
# Замените заглушки и не добавляйте .env в Git.
docker compose up --build -d
docker compose ps
docker compose logs -f app
```

Приложение доступно на порту 8080, SQL Server — 1433. Именованные тома сохраняют БД и старый каталог загрузок. Текущие аватары и фотографии врачей хранятся в SQL вместе с MIME.

Не публикуйте порт БД в production без продуманной сетевой защиты. Настройте резервное копирование, шифрование, минимальные права и ротацию секретов. Команда `docker compose down -v` удаляет тома с данными.

## Проверка выпуска

- [ ] Выпущен нужный коммит; отсутствуют ошибки запуска и миграций.
- [ ] `/health` возвращает 200 и здоровое состояние БД.
- [ ] Проверены история миграций и восстановление резервной копии.
- [ ] Секретов нет в журналах; HTTPS и защитные заголовки работают.
- [ ] Регистрация, вход, выход и разграничение ролей работают.
- [ ] Недопустимые межсайтовые запросы отклоняются.
- [ ] Служебные маршруты возвращают 401 без секрета.
- [ ] Некорректные и пересекающиеся записи отклоняются.
- [ ] Уведомления и модерация сохраняются в БД.
- [ ] Медиа сохраняется после нового развёртывания.
- [ ] Проверены «Дента», пять языков и арабский RTL.
- [ ] Результаты автоматических проверок изучены, исключения зафиксированы.

## Откат и инциденты

Остановите последующие выпуски, сохраните обезличенные свидетельства и определите источник: приложение, схема, провайдер или инфраструктура. Возвращайте предыдущую версию только при совместимости схемы; данные восстанавливайте по заранее проверенному плану. Отзовите раскрытые секреты и повторите проверки.
