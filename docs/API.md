# Справочник REST API

[Документация](README.ru.md) · [README проекта](../README.ru.md) · [English](en/API.md)

Приложение публикует JSON API под `/api`, SignalR hub `/hubs/notifications` и маршрут проверки здоровья `/health` с проверкой базы данных. Swagger UI доступен только в окружении `Development` по адресу `/swagger`.

Это справочник маршрутов и прав доступа. Точные контракты запросов и ответов определяются методы контроллеров и DTO в текущем коде.

## Аутентификация и доверие к запросу

Браузерная сессия — подписанный JWT в cookie `dc_auth`. Регистрация и вход задают cookie с `HttpOnly`, `SameSite=Strict`, корневым путём и `Secure` при HTTPS. Токен не возвращается в JSON и недоступен JavaScript браузера.

`JwtBearer` также поддерживает стандартный заголовок `Authorization: Bearer <token>`, если доверенная внешняя интеграция уже располагает токеном, однако штатные маршруты входа намеренно выдают только защищённую cookie.

Обозначения доступа:

| Метка | Значение |
|---|---|
| Public | Аутентификация не нужна |
| Patient | JWT role `Patient`; для ID действует проверка принадлежности |
| Admin | JWT role `Admin` |
| Super-admin | Сессия Admin и актуальная проверка `Admins.IsSuperAdmin` в БД |
| Cron | `Authorization: Bearer <CRON_SECRET>`; маршрут скрыт из Swagger |

В production запросы создания/изменения сессии и изменяющие состояние API-запросы с cookie должны поступать с того же источника. Платные AI-маршруты дополнительно отклоняют отсутствующий или cross-origin `Origin`. Development и Testing разрешают прямые запросы инструментов.

## Auth — `/api/auth`

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| `POST` | `/register` | Public | Регистрация пациента и создание защищённой сессии |
| `POST` | `/login` | Public | Вход пациента |
| `POST` | `/admin/login` | Public | Вход администратора |
| `POST` | `/logout` | Public/session-aware | Удаление cookie; обновление локального revocation cache при наличии claims |
| `GET` | `/session` | Patient/Admin | Восстановление несекретных UI-метаданных из проверенных claims |
| `GET` | `/profile` | Patient | Профиль текущего пациента |
| `GET` | `/admin/profile` | Admin | Профиль текущего администратора |
| `PUT` | `/profile` | Patient | Изменение имени/телефона текущего пациента |
| `PUT` | `/change-password` | Patient | Проверка и смена пароля, увеличение token version, завершение сессии |

Регистрация и оба маршрута входа ограничены 8 запросами в минуту на клиента в production. Email пациента/администратора уникален между ролями благодаря сериализованной прикладной логике и миграционным проверкам.

## Управление администраторами — `/api/admin-access`

Все маршруты требуют Admin JWT, после чего каждый метод проверяет актуальный статус суперадминистратора.

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| `GET` | `/` | Super-admin | Список администраторов и уровней доступа |
| `POST` | `/` | Super-admin | Создание администратора/суперадминистратора |
| `PUT` | `/{id}/super-admin` | Super-admin | Повышение или понижение |
| `PUT` | `/{id}/password` | Super-admin | Сброс пароля с отзывом старых сессий |
| `DELETE` | `/{id}` | Super-admin | Удаление другого администратора |

Сервис запрещает удалять собственную активную запись и удалять/понижать последнего суперадминистратора. Изменения в SQL Server сериализуются блокировкой приложения.

## Заявки на приём — `/api/appointmentrequest`

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| `POST` | `/` | Public/Patient | Создание гостевой или authenticated заявки |
| `GET` | `/patient/{patientId}` | Patient/Admin | Ограниченные active/history списки с проверка принадлежности |
| `GET` | `/admin/all` | Admin | Ограниченный CRM-список заявок |
| `PUT` | `/{id}` | Admin | Изменение расписания и допустимый переход статуса |
| `POST` | `/admin/phone` | Admin | Создание заявки по телефону |
| `PUT` | `/{id}/cancel` | Владелец/Admin | Отмена собственной pending-заявки |
| `PUT` | `/{id}/reschedule` | Владелец/Admin | Перенос собственной pending-заявки |

Публичное создание ограничено 3 запросами в минуту. Проверка расписания учитывает рабочие часы, часовой пояс клиники, lead time, шаг слота, длительность, активность врача и пересечения. Подтверждённую запись нельзя отменить/перенести через patient API — пациент направляется к контактам клиники.

При ограничении результата могут возвращаться headers `X-Result-Truncated`, `X-Active-Truncated`, `X-History-Truncated`.

## Ответы и ошибки

Большинство controller errors возвращают JSON с `message`. Некоторые операционные ответы содержат стабильный `code`, например transient database failure:

```json
{
  "message": "База данных временно отвечает медленно. Повторите запрос через несколько секунд.",
  "code": "database_temporarily_unavailable"
}
```

| Status | Значение |
|---|---|
| `400` | Некорректный request или запрещённый переход состояния |
| `401` | Нет валидной сессии/cron secret |
| `403` | Неверная роль, ownership, super-admin или origin |
| `404` | Ресурс не найден |
| `409` | Конфликт расписания, identity или catalogue integrity |
| `413` | Превышен request/file size |
| `422` | Экспорт выходит за безопасные операционные пределы |
| `429` | Превышена локальная/распределённая квота; ответ в production содержит `Retry-After: 60` |
| `503` | Временная проблема подключения к БД |

Пользовательские сообщения сервера пока смешивают русский и английский. Клиентам следует опираться на HTTP-статус и стабильный `code`, где он доступен, а не разбирать текст сообщения.
